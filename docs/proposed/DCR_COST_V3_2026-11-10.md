## 3. DCR-Cost v3

`algorithms/dcr_cost_v3/` (`dcr-cost-v3`, class `DCRCostPricedScheduler`). v1/v2 sources are untouched, so their
source hashes and stored results stay valid.

**Diagnosis.** On the instances with the largest gap to CP-SAT, v2's candidates give the first tasks of a wide
level the cheapest, slowest resources and pay for the lost time with the most expensive resources later. Every
single downgrade then overshoots D by a wide margin. A compensated pair move (one downgrade plus one speed-up on
the critical chain) was tried and did not help. The gap is in the candidate set, not in the local search.

**Method.**
1. *Time-priced candidates.* A list scheduler (ready task with the smallest σ_i first, exact insertion) places
   each task on the resource minimizing `c_ir + μ·t_ir` among the resources that finish by DCR's latest finish
   b_i (else the earliest finish). t_ir is the finish time or the duration (two modes); μ = S·2^k with
   S = Σ_i (cmax_i − cmin_i)/D and k = −8 … 8. That is 34 cheap runs; both grids are predeclared.
2. The 4 cheapest distinct priced plans that meet D get v2's downgrade improvement pass.
3. The cheapest of {v2's plan, improved priced plans} is polished: the same downgrade move, up to 8 cheaper
   resources per task, repeated until no move is accepted (at most 10·n exact rebuilds).

**Guarantee (conditional).** When v2 meets D, its returned plan is a candidate and every accepted move
lowers cost while retaining feasibility. Consequently, v3 is no more expensive than feasible v2 and
meets D whenever v2 does. When v2 misses D, a feasible priced candidate can cost more than v2's
infeasible schedule. The unconditional claim is not valid.

## 5. Tests

`tests/test_dcr_cost.py` (412 tests, new): internal makespan and cost equal the pinned evaluator's for v1/v2/v3;
dominance v1 ≥ v2 ≥ v3 in cost; the priced list scheduler's timing equals the evaluator's; the improvement
passes only lower cost, keep D and reach a local optimum; prefix resume equals a full rebuild; determinism,
seed rejection, independence from the budget. The whole suite passes locally: `2575 passed` (Python 3.13.18,
numpy 2.5.3). The Tests workflow passes on the branch, but it does not yet run the new file (see §7).

## 7. Limits and what is left

- **A sample, not the full set.** 495 of 1,890 expansion instances, run locally (2-core VM, 2 worker processes,
  so runtimes are indicative). 60-task instances are 55% of the sample and moderate QoS is over-represented
  among the larger ones, so read the per-size and per-QoS rows, not only the overall mean. The canonical run is the Benchmark workflow after merge:
  `set = expansion`, `algos = dcr-cost-v3`, `highlight = dcr-cost-v3`, `workers = 1`.
- **Design data.** The priced rule and its grids were first tried on 39 of the 60-task expansion instances, which
  are part of the sample above. Expansion is the development set for paper 2; no claim is made beyond it.
- **Runtime.** v3 costs 1.2–1.8x of v2. At 1,000 tasks the median is 51 s on this machine (v2: 33 s); the
  slowest run took 175 s.
- **Remaining gap.** Still up to 2.0x of the CP-SAT cost on single 60-task instances (montage).
- **CI.** The new tests are not executed by the current GitHub Actions workflow. A workflow update
  was attempted on 11 November and rejected by repository permissions/confirmation checks. Please
  add to `.github/workflows/tests.yml` after granting workflow-write permission:
  ```yaml
        - name: DCR-Cost algorithm and study tests (paper 2)
          run: python -m pytest -q tests/test_dcr_cost.py tests/test_dcr_cost_study.py
  ```
- The full per-run CSV of the study (0.6 MB) is not committed; `run` regenerates it.
